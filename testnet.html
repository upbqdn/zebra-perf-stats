Zebra perf stats: Testnet submitblock latency

Testnet network. Recorded Testnet observations. Static snapshot.

1. Abstract

The common unloaded Testnet subset contains 5 of 107 observed blocks, from 2026-10-26T12:57:51Z to 2026-10-26T14:34:03Z (UTC). Median dispatcher-observed RPC latency: Zakura: 1.6 ms (95% CI unavailable: insufficient pairs); Zebra v7.0.0: 2.9 ms (95% CI unavailable: insufficient pairs); Optimized Zebra: 1.7 ms (95% CI unavailable: insufficient pairs). Optimized Zebra build label: zebrad 6.2.2+1197.g89390f7 (source 89390f741931b5238a8ef94a86810d89b3320f1b, pasta-asm; sha256 f43267d0e7d9d084b63eb7af008091d13d42fd14b4b02a21b8691da0849f001f). Confidence intervals are exploratory; unavailable intervals are not evidence of zero uncertainty. These observations do not identify a causal effect of any individual code change.

Build strings are taken from recorded sessions and calls where present, otherwise from configuration. A differing current configured label is listed separately; it does not relabel past measurements. The comparison comprises 1 recorded session(s).

A feeder follows Testnet over P2P. The dispatcher sends each newly observed block concurrently to three isolated contestants using submitblock. Contestants have no peers and empty mempools; they do not independently follow public-network block propagation.

Latency is elapsed wall duration measured at the dispatcher from RPC request invocation through the parsed response using a monotonic high-resolution clock, not process CPU time. It includes request/authentication preparation, local RPC/HTTP overhead, server JSON parsing and block decoding, verification, state commit, and response transfer/JSON decoding. The request body is prepared before timing. This is not pure verification time. UTC timestamps are used for alignment and clustering, not for the latency duration.

Dispatch skew is the maximum first-send timestamp minus the minimum first-send timestamp across contestants. The common subset is selected once, before computing any headline node statistics, paired comparisons or latency figures:

  1. Select the first attempt for each node and block hash; retries never replace failed or catch-up first attempts.
  2. Require an accepted first attempt from all three contestants, with no catch-up flag.
  3. Exclude the first recorded block over 300 kB after each Zebra startup marker. Catch-up attempts also consume that startup slot.
  4. Require dispatch skew ≤25 ms.
  5. Exclude a block whose first dispatch falls in a recorded non-experiment workload interval, including its endpoints and ±30 seconds of padding. Overlapping padded intervals are merged; ongoing runs extend through export time.
  6. Exclude a concurrent block on the other network when this block's first-attempt window, from first dispatch through last response and widened by ±1 second, overlaps another-network submission window, including endpoints. Other-network first attempts span first dispatch through last response across targets; retries add individual windows without extending the original window across idle hours. Host-load shading remains separate from this exclusion.

Size bins use serialized bytes: kB = 1,000 bytes; both 20 kB and 300 kB belong to the middle bin. Percentiles use linear interpolation between ordered observations; p99 is reported only for n ≥100.

Paired differences are medians of same-block A − B values, not differences of marginal medians. Ratios are medians of same-block A / B values, not ratios of medians. Zero denominators are omitted from ratios only; the ratio sample count is reported separately. Positive differences and ratios above 1 mean A is slower than B.

All 95% confidence intervals use 2,000 bootstrap resamples of whole occupied UTC five-minute clusters with replacement, a fixed random seed of 0, and the 2.5th and 97.5th percentiles of the resampled medians. At least 20 observations (pairs for comparisons) and 12 occupied clusters are required. This procedure is used for node medians, paired differences and paired ratios; ratio intervals are dimensionless.

6. Threats to validity

  • Isolated, peerless nodes with empty mempools do not represent public-network propagation, mining, transaction admission or busy-mempool behavior.
  • Zakura uses pruned storage while the Zebra nodes use archive storage. Storage work and cache behavior differ.
  • The contestants share one 16-core host, CPU, memory and disks. Scheduling, compaction and contention can affect RPC durations.
  • The load filter covers recorded jobs, not every operating-system activity. “Unloaded” means outside those recorded intervals, not an otherwise idle host.
  • Restarts and catch-up affect caches and initialization beyond the first large block. Earlier unrecorded warm-up can make the startup proxy conservative.
  • RPC round-trip latency includes transport, parsing, verification and commit; it is not an isolated verification benchmark or CPU-time measurement.
  • The Testnet block-size mix changes over time and is not representative of every network. Serialized size does not describe transaction composition, and adjacent blocks can be correlated. Size bins and cluster resampling do not remove every source of dependence.
  • Optimized Zebra is a development stack. A recorded build comparison does not isolate a single optimization, establish causality, or predict all future builds and workloads.
